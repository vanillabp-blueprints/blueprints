# The header blueprint is a workflow module with a start form, and the module names who sees it

This repository keeps no decision log, so this file only makes the decisions visible when the
branch is merged. Dropping it is a fine outcome.

## What was decided

`cockpit-header-extension` comes in three parts like `cockpit-workflow-details`: backend, a React
frontend and the application. It has no cockpit of its own, no bundle and no application behind a
proxy. Its base is `cockpit-workflow-details-backend`, and the READMEs link the two earlier cockpit
blueprints for what is the same.

The button "Request a loan" and the start form are one visual entry, `StartForm`. The data entry
`Header` names the button, and the build checks it with `bc-check-entries --data-entry Header`.
`header(currentUser)` checks no rights. It returns nothing only while nobody is logged in, like the
example of the module kit.

Who sees the button is decided by the list of modules of the cockpit, as the story says. The
workflow module brings a `WorkflowModuleDetailsProvider` bean, `LoanApprovalModuleDetails` in the
`config` package, which names the group `LOAN_OFFICERS` as a constant. The endpoint of the start
form checks no group. Protecting endpoints stays with the blueprint about roles and permissions, as
in `cockpit-workflow-details`. The READMEs say so.

The integration test of the backend checks the groups in the bean, not in the cockpit. The dev shell
simulator stores the groups of a registration, but it shows them nowhere and has no list of modules
per user. The browser tests show the other half: a host whose list of modules leaves the module out
shows no button and loads no file of it. The README of the application shows the real cockpit of
its Docker Compose file answering the list for Jane and for John.

The second module of the browser tests is a small fixture with a manifest without `Header`, not the
build of `cockpit-user-task`. The frontend would otherwise need a second frontend build to test.

The start form posts JSON and gets 201 with the id of the new loan request. The module picks the
id. The endpoint refuses an empty applicant and an amount below 1 with 400. The generated record
does not check them, because the generator runs without bean validation in every blueprint, so the
controller checks them.

The blueprint reports no details of the case and adds no column to the case list. One pattern per
blueprint. The menu and pages of a module are named in the READMEs and not built.
