# Organizing user tasks: how the blueprint is cut

This repository keeps no decision log, as `CONTRIBUTING.md` explains. This file makes the
decisions of the blueprint `cockpit-organizing-usertasks` visible when the branch is merged.
Nothing cites it, so dropping it is fine.

## What was decided

The blueprint builds on `cockpit-usertasks-in-the-application`, not on `cockpit-user-task-*`.
Many of the patterns also hold for an application with forms of its own, and the base already
has a row per user task, which is where the editors of a task are kept. Its branch starts on the
branch of the base, so it is merged after the base.

The id is `cockpit-organizing-usertasks`, the default of the story. It does not start with
`cockpit-user-task-`, so `build_matrix.py` does not take it for a part of `cockpit-user-task`.

One blueprint shows all patterns, one section each. Only the four-eyes principle needs a model
of its own shape, two user tasks in a row, and the model has that. So no second blueprint is
needed.

The patterns are spread over three user tasks, so that each value can be shown with a reason
from the business: an assignee where the case belongs to one person, a candidate group where it
belongs to a team, and each of the three kinds of notification once.

Handing a task to other people is shown with a message boundary event which leads back into the
same task. The cockpit reads assignee and candidates only from the first report, and the
documentation of the cockpit advises this way.

The details providers are in `WorkflowTaskHandler`, next to the `@WorkflowTask` methods, as in
`cockpit-user-task-backend`. `BusinessCockpitService` is injected in `Workflow` only, like
`ProcessService`, so `Service` stays free of VanillaBP.

`vanillabp.cockpit.template-loader-path` is written in the configuration file of the module and
not in the application. The templates are part of the module, and `classpath:` serves every
module of an application, because the adapter looks below a directory named after the module.
The cockpit has no key per module for this. That is a finding for the cockpit.

The forms have no PUT. Drafts work as in the base, and leaving them out keeps the delta small.

The integration test asserts on a copy of every report, kept by a recorder in front of the dev
shell simulator. The simulator drops the excluded candidates, the admitted users and the kind
of notification, which are what the blueprint is about. That is a finding for the simulator.

There is no Quarkus twin yet. The category `cockpit` is still before its twin phase.
