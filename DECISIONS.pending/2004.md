# The Camunda 8 cluster of the CI follows the adapter

This repository keeps no decision log, so this file only makes the decision visible when the
branch is merged. Dropping it is a fine outcome.

## What was decided

`bin/camunda8_cluster.sh` no longer pins a Camunda version. It reads the adapter version from
the blueprint POMs (`camunda8-adapter.version`) and fetches the POM which that adapter
publishes. That POM names `io.camunda:camunda-client-java` with a plain version. The script
starts `camunda/camunda` in that version. `CAMUNDA_VERSION` still overrides it.

Why the published POM and not something else:

- The client in that POM is the one the adapter calls the lowest cluster version it accepts.
  The adapter logs the same value at startup.
- The adapter has a test which keeps a plain version there (`Camunda8PublishedPomTest`,
  decision 39 of the adapter).
- The root POM of the adapter is not published as a parent of the adapter. A consumer gets
  the flattened POM. So the line properties in the root POM cannot be read from here.
- The jar also carries the value (`META-INF/vanillabp/adapter-camunda8.properties`,
  key `camunda8.client`). Reading it means a larger download and unpacking, for the same
  number.

In CI the script uses `.github/workflows/github-packages-settings.xml` when `USER_TOKEN` is
set, as the build does. So no workflow file changed.

Renovate was the other option in the story. It was not taken. A Renovate rule would still keep
two numbers, and they could still drift apart between two runs of Renovate.

## What it found

The pin said 8.10.0. The adapter snapshot was built against 8.10.5. The cluster now starts
8.10.5. The script was the only place in this repository which named a Camunda image version.
The split repositories do not get `bin/`, so they had no pin to change.
