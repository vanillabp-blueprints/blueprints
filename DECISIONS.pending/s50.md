# The service class says `@Transactional`

This repository keeps no decision log, as `CONTRIBUTING.md` explains. The rule itself now lives
in `CONTRIBUTING.md`, rule 6. This file makes the decision visible when the branch is merged.
Nothing cites it, so dropping it is fine.

## What was decided

Every business service of a workflow module carries `@Transactional` on the class. Before, the
annotation was on the methods the API calls only, and the class Javadoc of many blueprints said
it was absent from the methods a task handler calls on purpose.

A method called by a workflow task joins the transaction VanillaBP opened for the task. So the
annotation does no harm there, and it shows that the method needs a transaction.

A method which throws a `TaskException` gets `@Transactional(noRollbackFor = TaskException.class)`
on Spring Boot and `@Transactional(dontRollbackOn = TaskException.class)` on Quarkus. A plain
annotation would mark the transaction of the task for rollback, and VanillaBP would fail the
task. The other way, overriding the annotation with `propagation = SUPPORTS`, was rejected. The
rollback attribute says what matters in the code, next to the `throw`.

`persistence-custom` keeps its service without the annotation. Its store is not part of a
platform transaction, so it opens the unit of work itself.
