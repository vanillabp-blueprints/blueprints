# bpmn-versioning deploys two versions in a second test

This repository keeps no decision log, so this file only makes the decision visible when the
branch is merged. Dropping it is a fine outcome.

## What was decided

The test with two boots is a second integration test in `bpmn-versioning`, not a blueprint of
its own, because it shows the same intent. It lives in the Spring Boot twin only, like the
restart test of `module-bpms-migration`. A Quarkus test boots the application once.

The first boot deploys an older model from the test resources of the application module. It is
the shipped model plus a timer of ten seconds before the risk assessment. The timer keeps a
workflow waiting while the first boot stops, without any code of its own. The second boot
deploys the shipped model, so the engine counts it as version 2. The test asserts the start
notice about the workflow which is still on version 1, and which method each workflow ran.

The test runs under `camunda7` only. The two methods split at version 1, and only an engine
which starts empty counts from one. In CI a Camunda 8 cluster already holds the shipped model
as version 1 from the module test. So the older model would become version 2, and the assertion
about which method ran would be wrong. Version tags for the methods would make it work there
too, but they would change what the blueprint teaches.
