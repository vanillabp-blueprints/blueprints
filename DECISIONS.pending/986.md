# Every blueprint which runs on Camunda 7 runs on Operaton, too

Like the other files here, this one makes a decision visible when the branch is merged. Nothing
cites it, and dropping it after the merge is fine.

## What was decided

Every blueprint with a `camunda7` profile has an `operaton` profile next to it. The profile
names the adapter `io.vanillabp:operaton-adapter-*` instead of the Camunda 7 one, with the same
scope. Each `application-camunda7.yaml` has an `application-operaton.yaml` next to it, with the
same settings for the adapter id `operaton`. The BPMN files of `processes/camunda7` are copied to
`processes/operaton` unchanged. Operaton reads their `camunda:` attributes, and the blueprints
show exactly that: a Camunda 7 model runs on Operaton as it is.

`bin/add_bpms_profile.py` does all of this, for every engine its table `ENGINES` knows. A fork
of Camunda 7 such as CIB seven is one more entry there. The script leaves a profile alone which
does more than add the adapter, and says so. That was `persistence-flyway`, whose profile takes
the engine's scripts out of the engine JAR. Its `operaton` profile and the Liquibase changelog
of `persistence-liquibase` were written by hand.

`operaton` runs in every build matrix, the pull request's included, like `camunda7`. A directory
the index does not know is built against every runnable engine again, Operaton included.

## module-bpms-migration

The blueprint shows a second migration, from Camunda 7 to Operaton, in the profile `operaton`.
Both engines are embedded, and that needs two things the migration to Camunda 8 does not:

- Operaton gets a database of its own, because two engines must not share one set of tables.
  Camunda 7 keeps its tables where they were before the migration.
- Camunda 7 and Operaton 2.2 bring the FEEL library in two versions, and the Camunda 7 engine
  does not start with Operaton's. So the Camunda 7 adapter loses its copy, and Camunda 7 uses
  its older FEEL implementation (decision 8 of the Operaton adapter).

The Camunda 7 adapter switches the FEEL implementation with its key
`vanillabp.adapters.camunda7.dmn-feel-legacy-behavior`, which the profile file sets. So no Java
file of the blueprint names a class of an engine. On Spring Boot `OperatonDatabase.java` builds
Operaton's datasource under the `operaton` profile only; on Quarkus the profile file declares it.
On Quarkus that datasource takes part in the two-phase commit (`transactions: xa`), because one
transaction writes to both databases.

The web applications of Operaton are not part of that profile. Those of both engines in one
application have not been tested together.
