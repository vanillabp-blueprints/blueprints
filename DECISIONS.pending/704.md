# The migration blueprint keeps one scoping mode, and the profiles have to agree

Read this before giving it a number: **this repository keeps no decision log on purpose.**
`CONTRIBUTING.md` says a register was removed here once every entry was closed, because keeping
it only invited citations into it, and it says a finding for the framework becomes a story in the
framework's roadmap rather than an entry here. The reasoning below therefore already lives where
this repository wants it, in the blueprint's own `README.md` and `AGENTS.md` and in
`CONTRIBUTING.md`. This file exists so the decision is visible when the branch is merged, not so
that something cites it. Dropping it is a fine outcome.

## What was decided

`module-bpms-migration` demonstrates one migration: the one between two BPMS. It does not change
`name-clash-avoidance` on the way, so the `camunda8` profile repeats the `use-prefix` the
`camunda7` profile set, for the `camunda7` adapter as well as for `camunda8`.

The other way round was possible: let the mode leave the `camunda7` profile so both profiles use
the default `by-adapter`. It was rejected because a Camunda 8 cluster from the stock image has
multi-tenancy switched off and rejects the tenant `by-adapter` asks for, which is why every
blueprint of this repository configures `use-prefix` and why `build.yaml` refuses to override it
from the environment.

## What was measured

On 2026-09-28, in `module-bpms-migration/springboot`, against the embedded Camunda 7 engine on an
H2 file database, with a throwaway test which boots the application twice over one database and
answers the message afterwards. Each case was run once, and the engine's own state was read
before the message was answered:

| before the restart |   after it   |                       the message                       |
|--------------------|--------------|---------------------------------------------------------|
| `use-prefix`       | `use-prefix` | correlates, the loan is paid out                        |
| `by-adapter`       | `by-adapter` | correlates, the loan is paid out                        |
| `use-prefix`       | `by-adapter` | `WorkflowNotFoundException`, the loan is never paid out |

Under `use-prefix` the engine held the process definition and the message subscription with the
workflow module id in front of the name and no tenant. Under `by-adapter` it held the plain names
in the tenant `loan-approval`. Both were read out of the engine in the boot which answered the
message.

The third row is what the blueprint did before this change, because the `camunda8` profile named
no mode for `camunda7` and the default is `by-adapter`. The engine kept the prefixed names while
the application asked for the plain ones in a tenant, so nothing was found. Every operation on a
workflow started before the switch is affected, not only the message: `bpmsHolding` fails the same
way, which is what the test now trips over first.

A single boot under either mode pays the loan out, so the mode is not wrong by itself. Only
changing it is.

## What notices it now

Two things, because one of them alone was not enough.

`MigrationRestartIT` drives the real switch: the first boot adds `application-camunda7.yaml` on
top of the migration profile, the second runs the migration profile alone. With the mode removed
from the `camunda8` profile again the test fails at the first operation on an old workflow
(measured: `WorkflowNotFoundException` at line 149). Before this change it passed, because both
boots ran one profile and imitated the state before the migration with a priority list.

`bin/check_scoping_modes.py` compares the profiles of every blueprint, counting the default as a
value, and fails when one adapter is left under two modes. It is in `checks.yaml`, needs no
cluster, and it covers the Quarkus twin, which has no restart test at all, and every blueprint
added later.
