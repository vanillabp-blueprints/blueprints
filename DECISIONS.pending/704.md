# The migration blueprint keeps one scoping mode, and the profiles have to agree

Read this before you give it a number: **this repository keeps no decision log, on purpose.**
`CONTRIBUTING.md` says that a register was removed here once every entry was closed, because
keeping it only invited citations into it. It also says that a finding for the framework
becomes a story in the framework's roadmap, not an entry here. So the reasoning below already
lives where this repository wants it: in the blueprint's own `README.md` and `AGENTS.md`, and
in `CONTRIBUTING.md`. This file exists so that the decision is visible when the branch is
merged, not so that something cites it. Dropping it is a fine outcome.

## What was decided

`module-bpms-migration` shows one migration: the one between two BPMS. It does not change
`name-clash-avoidance` on the way. So the `camunda8` profile repeats the `use-prefix` which the
`camunda7` profile set, for the `camunda7` adapter as well as for `camunda8`.

The other way round was possible: take the mode out of the `camunda7` profile, so that both
profiles use the default `by-adapter`. It was rejected. A Camunda 8 cluster from the standard
image has multi-tenancy switched off, and it rejects the tenant `by-adapter` asks for. That is
why every blueprint of this repository configures `use-prefix`, and why `build.yaml` refuses to
override it from the environment.

## What was measured

On 2026-09-28, in `module-bpms-migration/springboot`, against the embedded Camunda 7 engine on
an H2 file database. A throwaway test booted the application twice over one database and
answered the message afterwards. Each case ran once. The engine's own state was read before the
message was answered:

| before the restart |   after it   |                       the message                       |
|--------------------|--------------|---------------------------------------------------------|
| `use-prefix`       | `use-prefix` | correlates, the loan is paid out                        |
| `by-adapter`       | `by-adapter` | correlates, the loan is paid out                        |
| `use-prefix`       | `by-adapter` | `WorkflowNotFoundException`, the loan is never paid out |

Under `use-prefix` the engine held the process definition and the message subscription with the
workflow module id in front of the name, and no tenant. Under `by-adapter` it held the plain
names in the tenant `loan-approval`. Both were read out of the engine in the boot which
answered the message.

The third row is what the blueprint did before this change. The `camunda8` profile named no
mode for `camunda7`, and the default is `by-adapter`. The engine kept the prefixed names, while
the application asked for the plain ones in a tenant. So nothing was found. This affects every
operation on a workflow started before the switch, not only the message. `bpmsHolding` fails
the same way, and the test now trips over that first.

A single boot under either mode pays the loan out. So neither mode is wrong by itself. Only
changing it is.

## What notices it now

Two things, because one of them alone was not enough.

`MigrationRestartIT` drives the real switch. The first boot adds `application-camunda7.yaml` on
top of the migration profile. The second runs the migration profile alone. If the mode is
removed from the `camunda8` profile again, the test fails at the first operation on an old
workflow (measured: `WorkflowNotFoundException` at line 149). Before this change it passed,
because both boots ran one profile and imitated the state before the migration with a priority
list.

`bin/check_scoping_modes.py` compares the profiles of every blueprint, and counts the default
as a value. It fails when one adapter is left under two modes. It is in `checks.yaml` and needs
no cluster. It covers the Quarkus twin, which has no restart test at all, and every blueprint
added later.
