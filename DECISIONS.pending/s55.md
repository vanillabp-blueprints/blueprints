# The cockpit frontends generate their API client with @hey-api/openapi-ts, at every build

This repository keeps no decision log, as `CONTRIBUTING.md` explains. The rule itself now lives
in `CONTRIBUTING.md`, rule 7. This file makes the decision visible when the branch is merged.
Nothing cites it, so dropping it is fine.

## What was decided

The frontends of the cockpit blueprints, `blueprints-cockpit/*-frontend/<framework>`, call the
API of their workflow module. Until now they used `openapi-fetch` with types which
`openapi-typescript` wrote from the OpenAPI file. The calls themselves were written by hand, as
paths in strings.

Now the npm package `@hey-api/openapi-ts` writes the whole client from the OpenAPI file. Its
names follow the file the way the Java names of the backends do. The class name comes from the
tag: the tag `user-tasks` becomes the class `UserTasksApi`. An operation becomes a method, and a
schema becomes a type of the same name. The first server of the file becomes the base URL of the
client.

`openapi-ts.config.mjs` of each frontend sets the options:

- the plugin `@hey-api/sdk` with `operations: { strategy: 'byTags', containerName: '{{name}}Api',
  methods: 'instance' }`, so there is one class per tag with the name the Java client has,
- `paramsStructure: 'flat'`, so a method takes one object with all its parameters, and the body
  comes under the name of its schema,
- `responseStyle: 'data'` and `throwOnError: true` of the plugin `@hey-api/client-fetch`, so a
  method returns the data and throws when the answer is not a success.

The one instance in `src/shared/api.ts` is named after its role, not after its type:

```ts
export const loanApproval = new UserTasksApi();
await loanApproval.completeAssessRisk({ loanRequestId, taskId, assessRiskInput: { riskAssessment } });
```

Since blueprints#168 a form endpoint names the business id of the case and the task id, so the call
carries `loanRequestId` next to `taskId`. When this decision was taken, the call had only
`userTaskId`.

This is also how project M calls its generated client.

The generated client throws only the body of an answer which is not a success, without its
status. The OpenAPI files of the blueprints give errors no body, so the forms could not tell 404
from 409 or 400. `src/shared/api.ts` therefore adds an error interceptor which turns such an
answer into its own `ResponseError`, which carries the `Response`. A network error has no answer
and stays the error `fetch` threw. So the forms check `error instanceof ResponseError &&
error.response.status === 409`, as before.

- The generator runs at every build, from `npm run generate:client`, and writes to
  `src/generated/`, which git ignores. This is what the backends do with their Java code below
  `target/`. So the OpenAPI file stays the only source, and a changed API breaks the build of the
  frontend instead of the form in the browser.
- The generator is a Node program and an exact dev dependency in `package.json`. It has no
  install scripts and downloads nothing when it runs. So the build of a frontend needs Node and
  `npm ci`, and nothing else: no Java, no Maven, no download from Maven Central.
- The line of `@hey-api/openapi-ts` is still 0.x and breaks things in minor versions. So the
  version is pinned exactly, and an update is checked by hand.

## What was not chosen

- The OpenAPI Generator with the generator `typescript-fetch`, run by the npm package
  `@openapitools/openapi-generator-cli`. It is the tool the backends use, and it was the first
  choice of this story. But it is a Java program. The npm package is only a wrapper, which
  downloads the jar of the generator at the first `generate` and runs it with `java`. Many build
  agents for Node have no Java, and many may not download anything during the build.
- Committing the generated code. Then the build needs no generator at all, but every move of the
  git submodule `backend` needs somebody to generate again, and nothing stops a client which no
  longer fits the OpenAPI file. The Java code is not committed either.
- A small hand-written wrapper in `api.ts` which keeps the parameters positional, as the Java
  client has them. It would need one line of hand work per operation, and a blueprint should show
  how to use the generated client, not how to hide it.

## Who decided

Stephan, 2026-11-14, in the review of blueprints#149: "Es soll dieser Generator verwendet werden:
https://openapi-generator.tech/docs/generators/typescript-fetch/. Da kommen, analog zu Java,
benannte Klassen heraus." Generating at every build instead of committing the code follows the
Java side.

Stephan, 2026-11-16: the build of a frontend must not need Java, because the Node build agents of
customers have only Node, and it must not download anything during the build. So
`@hey-api/openapi-ts` replaces the OpenAPI Generator. The forms call the generated class directly
with the parameter object, as project M does. The calls do not have to look exactly as before,
but every status the forms tell apart (400, 404, 409 and a network error) must still be told
apart and handled as before.
