# A simulator plays the systems around a workflow module

This repository keeps no decision log, as `CONTRIBUTING.md` explains. The blueprint
`module-simulator` and the two changes to the checks in `bin/` carry the rules. This file makes
the decisions visible when the branch is merged. Nothing cites it, so dropping it is fine.

## What was decided

The simulator is a Spring Boot application of its own, a Maven module `simulator` of the
blueprint. It extends the dev shell simulator of the Business Cockpit, so it plays the cockpit
as well. The integration tests of the workflow module report to it with the real cockpit
adapter. There is no WireMock and no switch which turns the cockpit off.

The workflow module depends on ports, one Maven module per system, named after the role of the
system. The adapters are Maven modules of their own. Only the application depends on them, and
the workflow module only in its tests.

The test API of the simulator lives below `/simulator/test-api/{system}/{action}` and knows
nothing about the workflow. Its actions are GET requests, so a person can use them in a browser
like the API of the application. The caller gives the ids, or it reserves one with `next-id`.

The Maven profile `start-stop-simulator` of the workflow module starts the runnable JAR of the
simulator with the exec plugin, on a port the build helper plugin reserved, and lets the build go
on. The tests wait until the simulator answers. The exec plugin stops the simulator when the
Maven build ends, and not right after the integration tests. Stopping it there would need a
plugin which can only call HTTP or JMX, and the end of the build is soon enough. The profile is
on unless `simulator.base-url` names a simulator somebody started by hand. With the profile, a
test which finds no simulator fails. Without it, the test is skipped.

The profile of the application which chooses the systems is a second active profile next to the
BPMS profile: `spring.profiles.active: "@bpms@,${external-systems:local}"`. `local` points every
adapter at the simulator, `real` reads the addresses from the environment.

`bin/check_twin_diff.py` got a list `BLUEPRINTS_BEFORE_THEIR_TWIN_PHASE`, next to the list of
categories. `module-simulator` is a Spring Boot blueprint first, in the category `module`, whose
twin phase is over. Its Quarkus twin comes later.

`bin/check_scoping_modes.py` got a list `MODULES_WITHOUT_A_BPMS`. The simulator has an
`application.yaml` and runs no BPMS, so it has no BPMS profile to compare.

## Why

The application mocks nothing, so its real adapters are tested, and the same adapters run against
the real systems later. A test API which knew the process would break with every change of the
model. A `next-id` which does not reserve gives two tests the same data, and then the tests cannot
run at the same time.

## The service is transactional, the credit rating included

Stephan's review of 2026-11-13: `Service` says `@Transactional` on the class, like every service
of a blueprint. A method which a workflow task calls joins the transaction of VanillaBP, and the
annotation still shows that it needs one. `request` asks the credit rating inside that
transaction, so a database connection waits for the answer. The adapter's timeout keeps that
short, and splitting `request` into two classes would make the example harder to read for little
gain. The README and the Javadoc say so, and say what to do for a system which may take long.

## The simulator stays a dependency of the workflow module

The dependency with `<type>pom</type>`, scope `test` and the exclusion of everything orders the
build and puts nothing on a classpath. The order of `<modules>` does not replace it: Maven sorts
the reactor by dependencies, a parallel build runs independent modules at the same time, and
`mvn -pl loan-approval -am` leaves the simulator out entirely, so the copy of its runnable JAR
fails.

## Every API is an OpenAPI file, and its Java code is generated

Stephan's review of 2026-11-13: the interface between the application and a system the
simulator plays gets an OpenAPI file, and nobody writes its Java code by hand. Each system has a
Maven module named after its API, `credit-rating-api` and `e-signature-api`. It holds the
OpenAPI file and two modules, `client` and `server`, which generate the Java code with the
`openapi-generator-maven-plugin`. The application uses `client`, through the REST adapter. The
simulator uses `server`. The hand-written DTOs, paths and REST calls are gone.

A system which calls back has two OpenAPI files, one per direction: `e-signature.yaml` and
`e-signature-callback.yaml`. The modules follow the side, not the file. `client` holds the
client of the API and the interface of the callback, `server` the opposite.

The ports stay. The workflow module still knows `CreditRating` and `ContractSigning`, not the
generated client. The REST adapter is the code which uses the generated client and translates
its types into the types of the port. So the module keeps the language of the process, and the
generated code stays inside the adapter.

The generator settings are the same for every API and live in the root POM of the blueprint:
the generator `spring`, the library `spring-http-interface` for a client, `interfaceOnly` for a
server, `requestMappingMode: api_interface`, so the path of the `servers` entry goes onto the
interface and one simulator plays two APIs, records as models, and no Swagger annotations,
bean validation or jackson-databind-nullable. A client returns the body and throws on an error
status. Only the client of the callback in the simulator returns a `ResponseEntity`, because the
test API tells its caller which status the application answered. A Quarkus twin keeps the
OpenAPI files and the module layout and changes only the generator: `jaxrs-spec` with
`interfaceOnly` for `server`, and `java` with the library `microprofile` for `client`.

The envelope carries the whole address of the callback, as before. A generated client adds the
path of its API to its base address. So the simulator takes the path of the callback API off
the end of the callback address and uses the rest as the base. An address which does not end
with that path gets a 502 from the test API, with a message which says so.
