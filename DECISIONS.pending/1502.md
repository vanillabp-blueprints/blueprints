# The case page blueprint shows the status of the aggregate as a column, and no rights

This repository keeps no decision log, so this file only makes the decisions visible when the
branch is merged. Dropping it is a fine outcome.

## What was decided

`cockpit-workflow-details` comes in three parts like `cockpit-user-task`: backend, a React
frontend and the application. It has no bundle, no application behind a proxy and no route to an
nginx in the module. The README of each part links `cockpit-user-task` for what is the same.

A loan request is withdrawn through the process, and the process ends the normal way. The
page calls the module, the module correlates a message, and an interrupting event subprocess
ends the user task. Its service task sets the status of the aggregate to `WITHDRAWN`, and the
case reaches an end event. The cockpit reports the end as `COMPLETED`, and that is right:
withdrawing is a negative business outcome, not a run which went wrong. The case list shows the
status of the aggregate, which the details provider puts into the details of the case.

The word "cancel" stays away from this. `CANCELLED` in the cockpit means that somebody of
operations cancelled the process in the BPMS, so the run did not end the way it should. The
blueprint names its button, endpoint, message and status after withdrawing. Stephan decided
this in his review on 2026-11-13. The first version had written an outcome `CANCELLED` and had
planned to switch to the `endReason` of the cockpit later. Cockpit story 1847 is about the
operations case: the `deleteReason` of the engine as the first text of the comment.

The blueprint shows no rights. The story had asked for a role on the endpoint and the button.
That was decided before the review of `cockpit-user-task`, which moved all rights into a
blueprint about roles and permissions. The README says so.

The Camunda 8 model names the correlation key of the message itself, because the adapter adds
one for catch events and receive tasks only. Platform story 2154 asks the adapter to cover the
start event of an event subprocess as well.

A GET endpoint approves a loan request, for a human with a browser. It stands in for the form
of the user task, which is the subject of `cockpit-user-task`. So an approved loan request can
be seen next to a withdrawn one.
