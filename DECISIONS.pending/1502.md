# The case page blueprint shows the outcome as a column, and no rights

This repository keeps no decision log, so this file only makes the decisions visible when the
branch is merged. Dropping it is a fine outcome.

## What was decided

`cockpit-workflow-details` comes in three parts like `cockpit-user-task`: backend, a React
frontend and the application. It has no bundle, no application behind a proxy and no route to an
nginx in the module. The README of each part links `cockpit-user-task` for what is the same.

A case is cancelled through the process. The page calls the module, the module writes the
outcome to the aggregate and correlates a message, and an interrupting event subprocess ends the
case. The cockpit then reports the end as `COMPLETED`, because the process reached an end event.
So the case list cannot show "cancelled" from `endReason`, which the story had planned. The module
puts the outcome into the details of the case instead, and the frontend shows it as a column.
`LoanApprovalIT` checks both values, so it fails once the cockpit can say `CANCELLED` here, and
the blueprint has to follow then. Cockpit story 1847 asks how a module reports the reason.

The blueprint shows no rights. The story had asked for a role on the endpoint and the button.
That was decided before the review of `cockpit-user-task`, which moved all rights into a
blueprint about roles and permissions. The README says so.

The Camunda 8 model names the correlation key of the message itself, because the adapter adds
one for catch events and receive tasks only. Platform story 2154 asks the adapter to cover the
start event of an event subprocess as well.

A GET endpoint approves a loan request, for a human with a browser. It stands in for the form
of the user task, which is the subject of `cockpit-user-task`. So a case which ended the regular
way can be seen next to a cancelled one.
