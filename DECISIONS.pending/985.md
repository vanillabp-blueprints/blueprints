# Every blueprint which runs on Camunda 7 runs on CIB seven, too

Like the other files here, this one makes a decision visible when the branch is merged. Nothing
cites it, and dropping it after the merge is fine.

## What was decided

Every blueprint with a `camunda7` profile has a `cibseven` profile next to it, made the same way
as the `operaton` one. The profile names the adapter `io.vanillabp:cibseven-adapter-*`, version
`2.0.0-2.2-SNAPSHOT`, instead of the Camunda 7 one, with the same scope. Each
`application-camunda7.yaml` has an `application-cibseven.yaml` next to it, with the same settings
for the adapter id `cibseven`. The BPMN files of `processes/camunda7` are copied to
`processes/cibseven` unchanged. CIB seven reads the `camunda:` attributes and has no namespace of
its own.

`bin/add_bpms_profile.py` did this. `cibseven` is one more entry in its table `ENGINES`. Two
things differ from Operaton:

- CIB seven serves its web applications at `/camunda`, like Camunda 7.
- The web applications of CIB seven also start CIB seven's new webclient, and it does not start
  without a secret for its login tokens. So a profile file whose adapter configures `webapps`
  also sets `cibseven.webclient.authentication.jwtSecret`. The value is a demo value, like the
  demo user next to it, and the comment says how a real application makes its own.

`persistence-flyway` and `persistence-liquibase` were done by hand, as for Operaton. Flyway takes
CIB seven's scripts out of its engine JAR and leaves out the script of CIB seven's modeler,
because the adapter switches the modeler off. Liquibase includes the changelog CIB seven ships,
`org/cibseven/bpm/engine/db/liquibase/camunda-changelog.xml`. Its upgrade to 2.2 also creates
the modeler's tables, and the engine does not use them.

`cibseven` runs in every build matrix, the pull request's included, like `camunda7` and
`operaton`.

## module-bpms-migration

The blueprint shows a third migration, from Camunda 7 to CIB seven, in the profile `cibseven`.
It follows the one to Operaton: CIB seven gets a database of its own, because two engines must
not share one set of tables. On Spring Boot `CibSevenDatabase.java` builds it under the
`cibseven` profile only. On Quarkus the profile file declares it, and it takes part in the
two-phase commit (`transactions: xa`).

The FEEL part of the Operaton migration is not needed. Camunda 7 and CIB seven 2.2 use the same
FEEL library in the same version, so the POMs exclude nothing and the profile file does not set
`dmn-feel-legacy-behavior`.

Only the web applications of Camunda 7 are part of the profile. Those of both engines in one
application are not supported, because both read `camunda.bpm.*` and both want `/camunda`.
