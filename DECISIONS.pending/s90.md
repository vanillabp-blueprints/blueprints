# The resources of a workflow module live in a directory of its own

This repository keeps no decision log, as `CONTRIBUTING.md` explains. The rule itself now lives
in `CONTRIBUTING.md`, in the section on the package and file structure. This file makes the
decision visible when the branch is merged. Nothing cites it, so dropping it is fine.

## What was decided

`src/main/resources` of a workflow module, and of a library which belongs to one, holds only
`META-INF/` and a directory named after the workflow module ID. Everything else goes into that
directory. Spring Boot and Quarkus do not deploy a workflow module on its own, so all modules of
an application share one classpath, and the same path in two modules is a clash.

The details:

- The OpenAPI files move from `openapi/` to `<workflow-module-id>/openapi/`, for example
  `loan-approval/openapi/loan-approval.yaml`. This replaces the place decided in story S52,
  where the OpenAPI file was the second file outside the directory of the module.
- A library without a marker of its own, such as the test driver of `module-process-driver`,
  uses the directory of the workflow module it belongs to.
- An application module keeps its files at the top. It holds the modules together and has no
  neighbours on the classpath. `module-standalone` counts as an application, because there the
  application is the workflow module.
- `bin/check_module_resources.py` checks the rule in the workflow `Checks`.

## Who decided

Stephan, 2026-11-18, in his review of the blueprints: "openapi als Unterordner von loan-approval.
Da Workflow-Module in Spring-Boot und Quarkus nicht isoliert deploy-t werden (wie es z.B. bei
Java-Enterprise moeglich waere), muss durch Java-Packages fuer Klassen bzw. einem Unterordner fuer
Ressourcen ein Clash vermieden werden. Bitte alle Blueprints dahingehend pruefen." The exception
for application modules is the default the story set for that question.
